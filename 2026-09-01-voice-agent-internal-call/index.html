The headline: why heart problem returned a kidney doctor

This was the bug that made the agent look like it was hallucinating. It was not. Three ordinary steps chained into a wrong answer, and each step was individually reasonable.

CALLER SAYS:  "heart problem"
      |
      v
STEP 1  ── GPT-4o-mini "translates" it to clinical English
           "heart problem"  ->  "cardiovascular disease"
           the word HEART is now gone
      |
      v
STEP 2  ── the hardcoded shortcut in the code checks:
              words ∩ {heart, cardiac, cardio, palpitation, palpitations}
           "cardiovascular" is not in that set — exact match, not prefix
           SHORTCUT NEVER FIRES. nobody notices.
      |
      v
STEP 3  ── falls through to a keyword search that RANKS BY WORD COUNT

              64.00   NEPHROLOGY        cardiovascular x0   disease x96
               1.50   CARDIAC SCIENCES  cardiovascular x2   disease x1
               1.12   CARDIAC SCIENCES  cardiovascular x1   disease x1
      |
      v
RESULT:  NEPHROLOGY  — a kidney doctor for a heart complaint

The kidney list does not contain the word "cardiovascular" even once. It wins because it says the word "disease" 96 times. The one document that literally contains the phrase "cardiovascular disease" scores 1.50 and loses by a factor of forty.

The search picks the winner by counting how often a word appears, not by how meaningful the word is.

The second one is simpler

$text "hand pain":
   597.37   NEURO SCIENCES    hand x288   pain x640
   255.40   ORTHOPAEDICS      hand x0     pain x385

Orthopaedics has 4,377 keywords and not one of them is "hand". Neurology does have hand words — numbness, carpal tunnel — so neurology wins fairly. It is the only list that mentions hands at all. Same for fingers; "foot" appears only as diabetic foot under Endocrinology.

That one is not clever. Hands, fingers and feet were left out of the bone list.

The data behind it

Duplicate documents per department, five of them empty, sizes varying by two orders of magnitude. The query takes only the top result, so the biggest document tends to win regardless of relevance.

Why the keyword lists exist at all

Harshita's reason is a good one: callers speak Telugu and Hindi, so the lists carry local phrasings that map back to a department. The translation step exists for the same reason.

The problem is that translation runs first and destroys the exact word the shortcut is looking for. Srish's point on the call: the tool is never given a whole sentence. The agent already sends a short concern — headache, kidney stone, heart problem — so most of that machinery is being applied to input it was not designed for.

Decided

  • Booking IDs are exactly five digits and never start with zero. Below or

above that, the agent must not call the backend — it says the ID does not look right and asks again. Confirmed against the database: 586 of 586 appointments match, range 10394–99999. Reason for the leading-zero rule: if an ID were 01234, some layers would drop the zero and the same bug returns wearing a different hat.

  • B05 (invented ID "1234") is a prompt bug, not a backend one. The agent

fabricated the number itself; the backend simply answered the question it was asked.

  • B13 and B14 were triaged wrongly, and Srish said so on the call. The

agent was speaking failure scripts — "no doctor is available at Uppal", "I am unable to check the Uppal branch" — with no tool call at all. Nothing was called, so nothing failed and nothing found nothing. Merged into a new bug, B23.

  • B08 (Telugu selected, agent replies in English) is rejected — an Edesey

platform issue, not the prompt.

  • B11 (wrong doctor name in confirmation) is not an issue. Traced live on

the call: "Srikanth" was the patient's name and was used correctly.

  • Ophthalmology handling goes in the prompt, not the backend. TX Hospitals

has no ophthalmologist at any branch. When someone asks for one, the agent should offer a general physician or a receptionist transfer — never invent an eye specialist. Explicitly rejected doing this in the backend: "it should not be from backend, it should be from prompt itself."

  • Test on a separate deployment. A second API subdomain (UAT2) for these

changes rather than pushing straight to the environment QA is testing against. "Don't try to push it with that, because even we are unsure."

An open design question, not yet decided

Srish's instinct is to remove the big keyword-mapping database entirely and have the agent work out the department itself. The counter-argument raised is that the lists are what handle Telugu and Hindi phrasings.

Worth noting the choice is only ever between 25 departments. Picking one of 25 labels does not obviously need 100,000 keywords, and a bigger list makes the frequency scoring worse, not better — the largest document wins more often.

Wanted next: check_availability should return date ranges

Srish's spec, in his words on the call: when a date is given, return the slots for that date. When no date is given, return ranges, not a wall of dates:

    1–7 available
    8–14 available          (excluding 11, 12)
    15–21 available

Excluded dates in brackets. Far shorter than a list, and readable aloud.

Decisions that changed my own earlier analysis

Two calls I had made were wrong, and the transcripts settled it:

WasNow
B13 — "backend error surfacing correctly"No backend error. No tool call at all.
B14 — "working as designed"Same. The agent invented the bad news.

The cause was a hole in the prompt: the guard against inventing facts listed only positive ones — a branch name, a doctor's name, a time, a booking ID. Nothing stopped the agent inventing a negative: "no doctor is available", "I cannot check that branch". A polished failure sentence was sitting there with no precondition on it, so when the audio was unintelligible and the agent had to say something, that was the nearest thing to hand.
