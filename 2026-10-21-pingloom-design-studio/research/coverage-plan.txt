# Screen catalog coverage plan

The catalog covers the Product A path from public discovery through account verification, workspace setup, server credential handling, event ingestion, provider-attempt review, mobile receipt, shared acknowledgement, device revocation, usage, privacy and operational review. The web inventory contains 35 routes; Android contains 16 screens; iOS contains 16 future design references. IDs are platform-prefixed so the static review can filter routes without inferring platform from route syntax.

P0 entries represent the current Android, web and API product scope. P1 entries cover paid-beta capabilities such as invitations, webhook sources, billing, advanced analytics and service status; each carries an explicit implementation gate. iOS entries are marked Future because APNs/iOS is outside the current release. The route strings are catalog labels for proposed UI navigation and do not claim that API routes or product screens are implemented.

The inventory follows the product’s separate authentication domains: browser and mobile sessions are user credentials, while project API keys remain server-only and are shown once. It includes project/channel lifecycle, membership checks, one-time key reveal and revocation, a dashboard test-event playground, event search and detail, server-confirmed device readiness, quota boundaries, per-user read state, one shared acknowledgement, expired/revoked invitations, and logout-time device association revocation. It also represents denied notification permission and offline cached inbox behavior so the core receiver remains usable without push permission or connectivity.

Route-specific states identify meaningful page behavior and failure cases. Shared contract for every primary web route is loading, empty where relevant, forbidden, expired session and service error; the mobile equivalents are loading, empty where relevant, authentication/membership denial, offline where relevant and service error. Screens should surface only the states applicable to their data and actions, while preserving clear recovery paths. No state should imply successful provider delivery: API acceptance, provider acceptance, retry/failure and device display remain distinct.

The catalog keeps sensitive data out of UI content: no real API keys, FCM tokens, reset/invitation secrets or raw sensitive payloads. It flags server-side tenant enforcement, safe action URLs, secret redaction and honest quota semantics at the routes where those rules matter. P1 and Future entries are design coverage only until their backend, policy and operational gates are met; they must be labeled Coming soon or omitted from active navigation until functional.
