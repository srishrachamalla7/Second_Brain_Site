# PingLoom iOS concept plan

**Status: future concept only.** The PRD places iOS/APNs in P2 (§4) and makes Product A Android-first (§6, §15, §17). This document is a design reference for a future scope decision; it does not approve or start iOS implementation. Confirm product scope, APNs/backend support, delivery semantics, and platform policy at implementation time. Do not present iOS screens or controls as available in the current product.

## Product and navigation direction

Design this as a native SwiftUI companion for a shared developer-alert inbox. Its central task is to scan incoming events, inspect one, mark it seen personally, and optionally acknowledge it for the team. Keep the mobile experience focused on acting on alerts; project setup and API-key management remain dashboard-first. Never put a server API key in the iOS app.

Use a persistent three-tab iPhone structure: **Inbox**, **Projects**, **Account**. Inbox is the default. Projects holds project/channel context and per-user subscriptions; Account holds profile, workspace choice, notification preferences, device status, privacy, and sign-out. Keep event filters, search, and event actions in their relevant screens or toolbars, not as extra tabs. Preserve independent navigation and list/filter state per tab. On iPad, reassess the same destinations with an adaptive sidebar/split layout rather than scaling the phone UI.

Use standard SwiftUI navigation containers and typed destinations for event/project routes. Support system back gestures and restore the list position and filters on return. A push tap opens the event detail within Inbox; if authentication is needed, resume that destination after sign-in. Validate workspace membership on the server before showing the event. A missing, deleted, or forbidden event gets a non-revealing “This event is unavailable” state with a route back to Inbox.

Prefer system typography, controls, and SF Symbols. Use semantic text styles and semantic system colors so type scales with Dynamic Type and adapts to appearance, contrast, and transparency settings; use a restrained brand tint for selected navigation and primary actions. Avoid fixed font sizes and raw light-mode-only color values. Support VoiceOver labels and state, Reduce Motion, safe areas, and at least 44 pt hit regions. Give priority and read state a text or shape cue as well as color. Use native materials where system components provide them; do not make event cards glassy. Apple’s current HIG describes Liquid Glass as a functional navigation/control layer and recommends using it sparingly, with standard materials in content. Recheck these platform-specific conventions when implementation begins.

## Notification, privacy, and Focus behavior

- **Permission:** Follow Apple’s request-in-context guidance. Explain what PingLoom alerts contain, then request authorization following an explicit user action. If the user declines or continues without it, the authenticated inbox, history, read state, and acknowledgement remain usable. Explain how to change system settings without repeatedly prompting. Refresh authorization state when the app becomes active.
- **Preview privacy:** PRD requires minimal lock-screen previews by default. Keep push payloads minimal and non-sensitive (for example, a generic “New PingLoom event” summary); do not send the event body, raw `data`, API credentials, or sensitive identifiers in the push. Fetch event content through the authenticated API after a tap. The OS controls preview visibility, so explain that system setting rather than claiming the app can override it. Any future in-app “show detail in previews” option requires explicit product/security review and matching server behavior.
- **Focus and scheduled delivery:** Respect system delivery choices. Do not claim to detect which Focus is active or why a notification did not appear. Do not bypass Focus or scheduled delivery, and do not mark ordinary alerts as urgent/time-sensitive to force attention. If user-configurable quiet hours are implemented later, they remain an in-app preference and must match the server’s actual routing behavior; PRD places quiet hours in P1.
- **Delivery language:** The app can show server/FCM/APNs provider states only as the API defines them. A provider acceptance is not evidence that iOS displayed, delivered, or was read. Do not show a false success state when APNs credentials or registration are unavailable.

## Native iOS differences from the Android product

| Area | Future iOS concept | Android PRD baseline |
|---|---|---|
| Top-level navigation | Native iOS tab bar for Inbox, Projects, Account; preserve per-tab navigation. | Android implementation uses Kotlin/Compose and Material 3; choose Android navigation using Material conventions and do not copy the iOS tab treatment mechanically. |
| Push transport/device status | APNs authorization and token registration, with distinct permission, token, and server-confirmed registration states. APNs integration is future scope. | FCM token registration/refresh; PRD specifically requires Android 13+ runtime notification permission and server-confirmed `Ready`. |
| Permission UX | Request authorization contextually and treat system settings as the authority. Apple says the initial decision is remembered; re-read settings because people can change them. | Android 13+ permission flow is part of current M3; the app must retain inbox utility when denied and offer Settings recovery. |
| System presentation | Respect iOS notification settings, Focus, and scheduled delivery; use neutral copy and minimal content. | Android has notification channels; PRD calls for stable channels based on priority and minimal lock-screen previews. Do not assume channel controls map 1:1 to iOS. |
| Native accessibility | Dynamic Type, VoiceOver, semantic system controls, iOS safe areas, and HIG touch regions. | Compose/Material semantics, Android accessibility services, density units, and platform navigation behavior. Share product meanings, not platform-specific widgets. |

## Scope and implementation gates

Before any build work, the product owner must decide whether iOS becomes a funded/approved roadmap item and define its release priority. Then verify current Apple developer requirements and SDK guidance; provision APNs capabilities/credentials; extend the device/API contract for platform-specific registration; define per-platform delivery health; and add iOS device, permission-denial, tenant-isolation, deep-link, read, acknowledgement, logout/revocation, and privacy-preview acceptance coverage. Until these exist, label iOS as future scope and avoid active UI controls or claims of APNs support.

## Guidance and sources

- UI/UX Pro Max `--stack swiftui` query: `native inbox navigation accessibility privacy`. Matched recommendations: typed destinations with `.navigationDestination(for:)`, `@Environment(\.dismiss)` for dismissal, and accessibility labels for controls. Treat as design guidance, not a platform-version commitment.
- Apple, [Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars): tab bars are for top-level navigation, preserve section context, should have labels, and should not be hidden/disabled when content is unavailable.
- Apple, [Asking permission to use notifications](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications): request in context, request only notification interactions the app uses, and recheck current notification settings.
- Apple, [Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications): provide a generically descriptive hidden-preview placeholder and keep notification content discreet.
- Apple, [Managing notifications](https://developer.apple.com/design/human-interface-guidelines/managing-notifications): get permission, give in-app notification controls, and account for Focus/delivery preferences without over-interrupting people.
- Apple, [Materials](https://developer.apple.com/design/human-interface-guidelines/materials): Liquid Glass is a control/navigation material; keep it sparing and use standard materials in content.
- Apple, [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) and [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons): support Dynamic Type/accessibility and provide at least 44×44 pt button hit regions.
- PingLoom PRD §§4, 6, 8–9, 14–17, 20: iOS/APNs is P2; personal seen state and shared acknowledgement are distinct; push payloads stay minimal; user sessions are separate from server API keys; verify Apple/platform requirements when implementation begins.
