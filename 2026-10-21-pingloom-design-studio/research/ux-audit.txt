# PingLoom prototype UX audit

**Purpose:** Review the existing UX plans for a seven-page browser prototype. The prototype is a review artifact, not Product A, a working SaaS, or evidence that backend or native acceptance criteria pass. Keep the screens and sample data aligned with the PRD and make simulated behavior visible.

## Findings to resolve in the prototype

1. **Keep P1 team and billing concepts out of active P0 flows.** The PRD says workspace invitations and the team journey in §5, but classifies Teams as P1 in §4, the dashboard screen list in §7, and milestone M5 in §17. The web plan correctly gates `/team` as P1. The prototype may show a clearly marked “Coming soon” roadmap card, but must not offer functioning-looking invite, role mutation, checkout, or billing controls. A team invitation scenario is conceptual until M5. Similarly, Usage may summarize implemented P0 counters only; plan/quota management and billing remain P1. Sources: PRD §§4–5, 7, 12, 17; `web-plan.md` “Route and page plan” and “Role and phase gates”; `android-plan.md` “Screen inventory and scope.”

2. **Do not imply arbitrary members can create or manage keys.** The PRD and web plan authorize key create/rotate/revoke to owner/admin; members may inspect only if the real API permits, otherwise show a clear forbidden state. Never render a key in the dashboard preview or store it in browser state. The key-creation concept must communicate the one-time reveal, safe server-only use, copy action, and that leaving/closing loses access. Sources: PRD §§10.1, 14; `web-plan.md` route `/projects/:projectId/keys` and “Role and phase gates”; `AGENTS.md` “Two auth domains.”

3. **Align all team and delivery language.** Acknowledgement is one shared event state with actor/time; “Seen” or “Read by you” is personal. FCM/provider acceptance must never appear as device delivery. Use the PRD’s exact semantic states (`Accepted`, `Queued`, `Provider accepted`, `Retrying`, `Failed`) and explain that provider acceptance does not confirm display. If “Submitted to FCM” is used as explanatory copy, pair it with the canonical provider state. Avoid “Delivered,” “Received,” and phone-delivery success claims. Sources: PRD §§5, 8 FR-09/11, 9; `web-plan.md` “Product frame”; `notifications-plan.md` “State language”; `android-plan.md` “Inbox and detail interaction details.”

4. **Keep event detail private by default.** Inbox and lock-screen preview controls must have a generic/default-private state. Do not expose event body, data, action URL, API keys, tokens, or customer identifiers in a lock-screen mock. A preview preference is only a concept unless implemented; it cannot override OS lock-screen privacy. Event details and action URL are shown only in the authenticated app concept, and the link requires an explicit user action. Do not imply the server fetches customer URLs. Sources: PRD §§6, 9, 14; `notifications-plan.md` “Content templates”; `android-plan.md` “Open and act on an alert.”

5. **Make role and tenant context visible at the point of action.** Show current workspace and project on authenticated screens. Switching workspace changes all visible lists/metrics together and clears stale detail/filter context; project-scoped pages must not silently fall back. Provide a representative forbidden/access-lost state without revealing whether a cross-tenant ID exists. In the prototype this is an explanatory, deterministic sample, not a security test. Sources: PRD §§8 FR-01/12, 14; `web-plan.md` “Navigation and page behavior,” “Shared states,” and “Role and phase gates”; `AGENTS.md` “Tenant isolation.”

6. **Resolve test-send ownership in copy.** The PRD places “Send test” on Android Device status (§6), while Journey A and the web plan put the API playground/test event in the dashboard (§5; `web-plan.md` `/projects/:projectId/playground`). The seven-page browser prototype should put any send action in the dashboard playground and label it as a simulated sample action. Do not imply Android can send a server-authenticated API-key request or that a sample click dispatched a real push. Reconcile the Android control with the eventual API before native implementation.

7. **Keep iOS visibly future-only.** iOS/APNs is P2, is outside Product A, and requires separate approval. Do not include iOS as a working destination, active platform selector, or available notification channel. If the prototype retains an iOS illustration from the iOS concept plan, label it “Future concept · Coming soon” and make it non-interactive. Sources: PRD §§2.3, 4, 17 M6; `ios-plan.md` opening scope note; `notifications-plan.md` “iOS/APNs future boundary.”

## Browser prototype acceptance checks

These checks establish that the review prototype is navigable and understandable. They do **not** establish server authorization, persistence, delivery, or native behavior.

- **Theme persistence:** Light/dark selection updates every page/component, preserves readable contrast and focus states, and survives reload/navigation using the prototype’s declared persistence mechanism. System theme is the initial fallback if no user choice exists. A failed storage read falls back safely without blocking navigation.
- **Screen catalog:** Category/search filters update the visible screen cards and result count; clearing filters restores the full catalog; a no-match message and reset action appear. Filtering and expansion work by keyboard, with visible focus and semantic selected/expanded states. No hidden card is left focusable.
- **Phone screen picker:** Each available screen can be selected by keyboard or pointer; the selected screen is visibly and programmatically identified. The preview title/content changes to match, selection remains stable through theme changes, and unsupported P1/P2 screens are clearly marked as concepts/coming soon rather than represented as available app screens.
- **Sample acknowledgement:** Acknowledge on the designated synthetic event changes only that local sample to “Acknowledged by [sample name] · [sample time]”; a second activation does not create a second result. Other events remain unchanged. Provide a reset-to-sample-state control or clear reload behavior. Clearly label this as local prototype state; never show a toast or copy that implies a server write or team-wide synchronization.
- **Preview controls:** Web, phone, and lock-screen previews visibly reflect their selected scenario. The default lock-screen preview contains generic title/source only, no customer body or secret. Any expanded-content preview is explicitly opt-in and privacy-labeled. Priority is conveyed by text plus icon/shape, not color alone. State, personal read status, and shared acknowledgement are not conflated.
- **Keyboard and assistive technology:** Every link, button, select, filter, disclosure, and picker is reachable in logical visual order; Enter/Space work where expected; Escape closes transient overlays; focus remains visible and is not obscured. Include a skip link and page landmarks/headings. Icon-only controls have accessible names; decorative icons are hidden from assistive technology. Changes to filters/counts and sample acknowledgement are announced without moving focus unexpectedly. Forms use persistent labels and inline errors.
- **Reduced motion:** With `prefers-reduced-motion: reduce`, nonessential transitions/scroll effects are removed or shortened; selection and status changes remain immediate and understandable. No animation is needed to discover state.
- **Small viewport and zoom:** At 375 CSS px, all seven pages and interactive previews remain usable without page-level horizontal scrolling, clipped controls, or hidden actions. At 200% browser zoom, content reflows and keyboard focus stays visible; long keys/example payloads wrap or scroll inside their own labeled region. A horizontally scrollable data table, if present, is keyboard-accessible and has a clear caption/label.
- **Landscape:** At a short landscape viewport, page navigation, preview picker, and primary actions remain reachable; fixed/sticky elements do not cover content. Phone frame may scroll within its region, but key actions cannot be trapped below an inaccessible crop.
- **Semantics and legibility:** Contrast meets 4.5:1 for normal text and 3:1 for meaningful control boundaries/icons in both themes. Status, priority, selected filters, permission, and error states include text or accessible labels rather than relying on color. Interactive targets meet at least 44×44 CSS px where practical; focus styling is not removed.
- **Prototype honesty:** Every simulated action is labeled where it occurs. No fabricated live counts, delivery receipts, successful signup, key creation, invitation, billing, device registration, or server confirmation. Sample event data is synthetic and contains no real people or credentials.

## Genuine Product A acceptance gates (separate from the browser demo)

Passing the prototype checks above is not a milestone acceptance. The real product still needs these independently verified gates:

- **Auth, roles, and isolation:** Real email verification/session refresh/logout; owner/admin/member checks enforced server-side; every relevant object read/mutation tenant-filtered; negative cross-workspace ID tests; safe forbidden/not-found behavior; one-time API-key plaintext backed by hash/prefix storage; members cannot create keys. No API key in Android or client JS.
- **Durable ingest and honest status:** Valid server key request returns 202 only after event and outbox commit; idempotency same-payload replay returns original event and changed-payload reuse returns 409; validation/rate/quota errors remain distinct; worker retry is idempotent; provider acceptance is never called delivery. Local mock provider is visibly simulated, and absent Firebase credentials block real push rather than fake success.
- **Acknowledgement/read:** Read state is per user; one authorized shared acknowledgement wins with actor/time; retries and concurrent requests converge; UI does not claim success before server confirmation. Test with two authorized users/devices and one unauthorized user.
- **Privacy/device lifecycle:** Push payload is minimal; full event requires authenticated fetch; lock-screen privacy defaults generic; permission denial leaves inbox usable; registration shows Ready only after server confirmation; token refresh updates only after confirmation; logout revokes device association and clears account data.
- **P0 route completeness:** Every primary route has appropriate loading, first-use empty, filtered-empty, forbidden/access-lost, expired-session, offline/service-error and retry states. Actions have real backing behavior; unimplemented P1/P2 is hidden or clearly “Coming soon.”
- **Native Android usability:** Verify Android 13+ permission grant/denial/settings recovery, real FCM lifecycle, TalkBack order/labels, 48 dp targets, large font, dark/light contrast, reduced motion, safe areas, 375 px-class phone, landscape, and no action hidden behind system bars. These require an emulator/device and backend/provider environment; a browser phone mock cannot pass them.
- **Web production usability/security:** Verify real session expiry and tenant switch, role restrictions, API playground behavior without client-held server keys, URL/filter deep links, keyboard and screen-reader behavior, browser zoom/responsive reflow, and Playwright E2E against the actual app/API. A static prototype cannot establish these.
- **Release scope:** iOS/APNs and Product B remain excluded until separately approved; P1 team invitations/billing remain gated until M5 behavior and tests exist. Do not claim production launch, real delivery, billing, or store publication based on design or demo evidence.

## Basis

Primary source is `PingLoom_PRD_v1.0_AI_Build.md` (especially §§4–9, 10, 14, 17–18) and the repo `AGENTS.md`. Reviewed plans: `web-plan.md`, `notifications-plan.md`, `android-plan.md`, and future-only `ios-plan.md`. Native accessibility/layout gates also follow `ui-ux-pro-max/references/pro-rules.md`; the general UI/UX Pro Max priority order places keyboard accessibility, touch interaction, responsive layout, contrast, forms, and reduced motion ahead of decorative polish. The plan files are design guidance, not evidence that an implementation exists.
