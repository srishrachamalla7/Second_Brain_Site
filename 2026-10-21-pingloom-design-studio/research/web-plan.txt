# PingLoom web experience plan

## Product frame

The web app is the setup console and operational record for Product A: developers configure projects and channels, create server-only credentials, send a test event, then inspect what the API accepted and what the provider accepted. Make that path obvious before adding dashboard ornament. The audience is developers setting up an integration and small teams checking an alert during work.

The interface must distinguish **accepted**, **queued**, **provider accepted**, **retrying**, and **failed**. Provider acceptance does not prove a phone received or displayed a notification. `Seen` is per user; `Acknowledged` is one shared event state. Do not use “delivered” as a status. The dashboard never exposes server API keys to browser JavaScript or suggests putting them in client code.

## Visual and interaction direction

Use a calm, light-first developer console with strong typographic hierarchy, quiet borders, compact data tables, and a restrained teal/green action color. Give code and IDs a monospace face. Keep status meaning in text and icon as well as color; reserve red for destructive or failed states. The built-in UI/UX Pro Max design-system search matched a minimal Swiss style, IBM Plex Sans / JetBrains Mono, and a technical code-forward treatment. Its broad query resolved to a documentation landing pattern, so apply its visual guidance to the console but use the PRD's operational dashboard structure for product pages.

Use consistent spacing, predictable page titles and breadcrumbs, and one primary action per page. Icons are SVGs with accessible names when they are the control; avoid emoji. Every interactive target has a visible keyboard focus state, and keyboard order follows the page. Forms have persistent labels, inline errors, and a linked error summary that receives focus on failed submit. Respect reduced motion, keep contrast at least 4.5:1 for normal text, and support 375 px through desktop widths without horizontal page scrolling. On narrow layouts, collapse the sidebar into a labeled menu, turn wide tables into stacked rows or a deliberate column selector, and keep essential actions reachable.

## Information architecture and navigation

### Public routes

- `/` — product explanation, the five-minute setup sequence, honest delivery semantics, pricing experiment where approved, and a clear sign-up CTA.
- `/docs` and `/docs/*` — quick start, API reference, authentication and event limits, status semantics, and troubleshooting. Keep examples consistent with implemented contracts.
- `/login`, `/register`, `/verify-email`, `/forgot-password`, `/reset-password` — account access and recovery.
- `/invite/accept` — accept an expiring workspace invitation (P1; a direct link may resolve to sign-in first).

### Authenticated app routes

Use a persistent left navigation rail on desktop and a compact drawer on small screens. Its top area contains workspace switcher; the project selector is contextual and changes project-scoped pages. Main navigation: **Overview**, **Projects**, **Events**, **Devices**, **Usage**. A lower **Workspace settings** group contains **API keys** (project-scoped), **Settings**, and P1 **Team**, **Webhook sources**, **Billing**. Place **API playground** as a prominent project-level action and also link it from onboarding and project detail. Preserve selected workspace/project in route parameters or a stable URL, and deep-link filters and event IDs.

Show the current workspace and project in breadcrumbs/page headers. A workspace switch changes every list and metric scope together. Project pages must never silently fall back to a different project. Do not expose routes or navigation for Product B, embedded SDKs, iOS/APNs, or web push.

All P0 routes share the global loading, empty, forbidden, expired-session, and service-error behavior below; the table calls out route-specific content and empty/error details.

## Navigation and page behavior

- Workspace switcher is available from every authenticated page. Switching workspace resets invalid project context, filters, and active detail state; show the new workspace in the page header before rendering its data.
- Project selector is available wherever a page is project scoped. Project detail, channels, keys, playground, and event filters share the same selected project.
- Provide breadcrumbs for nested pages and a visible page title. Use standard browser history and deep links; back from event detail returns to the explorer with its filters intact.
- Destructive actions (archive, revoke, rotate, remove, delete) name the exact object and consequence. Confirm in a dialog with keyboard focus trapping and return focus to the initiating control on close.
- Long-running actions show an in-place pending state, disable duplicate submission, and report the server result. Never use a generic “Success” toast as the only evidence for important actions.
- API errors use the shared envelope's safe message and request ID. Give a retry action only for retryable conditions; preserve the form/payload. Never display stack traces or credentials.

## Shared states for every primary app route

1. **Loading:** retain page shell and title, use skeletons sized to final content, announce dynamic updates without repeatedly moving focus. Don't render a false empty state while fetching.
2. **Empty:** explain what is absent and give one next action that is available to the current role. Distinguish “not configured,” “no events in this range,” and “no data available.”
3. **Forbidden:** explain insufficient access without confirming another tenant's object exists; link back to an authorized overview. Hide unauthorized actions as well as enforcing server-side denial.
4. **Expired session:** preserve a safe return URL, explain sign-in is needed, and resume after authentication where possible. Do not lose unsaved form data silently.
5. **Service error:** human-readable safe message, request ID, and relevant retry/back action. Keep stale data visibly timestamped if retained; never make it look current.
6. **Offline/transient:** show connection state and last updated time; allow safe retry. Do not optimistically mark an event acknowledged or a device ready before confirmation.

## Role and phase gates

| Capability | Owner | Admin | Member |
|---|---|---|---|
| View workspace overview, authorized projects/events, usage | Yes | Yes | Yes, within workspace and subscribed-channel policy |
| Create/manage projects and channels | Yes | Yes | No |
| Create/rotate/revoke API keys | Yes | Yes | No; show read-only explanation |
| Send playground event | Yes | Yes | Only if backend grants appropriate permission; otherwise disabled with reason |
| Read event and mark personal seen / shared acknowledge | Yes | Yes | Yes, within authorized scope |
| Manage invitations/roles | Yes (P1) | Yes if policy grants it (P1) | No |
| Billing, plan change, workspace deletion | Yes (P1) | No | No |

Authorization is server enforced on every read and mutation. UI gates improve clarity but do not replace tenant/project membership checks. P1 pages remain absent or explicitly Coming soon until their complete backend path exists; no simulated controls or fake billing/team success.

## Delivery phases

**P0 web foundation and setup:** public landing/docs; authentication and recovery; workspace/project onboarding; projects and channels; safe one-time key lifecycle; dashboard overview; authenticated playground; event explorer/detail; device readiness; read-only usage; profile/workspace settings. Prioritize the vertical first-alert flow and error/empty/permission states alongside each route.

**P1 paid beta:** team invitations/roles and channel subscriptions, webhook sources with secret lifecycle and safe validation, advanced filters/retention/health where implemented, plan restrictions, hosted checkout/portal, verified billing webhooks and invoices. Release each navigation item only when its end-to-end behavior and authorization are ready.

**Out of scope for this web plan:** Product B customer-app SDK configuration, iOS/APNs, web push, arbitrary workflow/code execution, SMS/email campaigns, and unimplemented analytics presented as live.

## Review checklist

- Can a first-time developer go from signup to a valid test event without guessing what to do next?
- Does the page distinguish API acceptance from provider acceptance and actual device/user evidence?
- Are API key plaintext and FCM tokens absent from later views, logs, and browser client state?
- Do all primary routes have loading, empty, forbidden, expired-session, service-error, and retry behavior?
- Are project/workspace scope and role visible, and are unauthorized objects protected without existence leaks?
- Are all controls functional for the current phase and role, with keyboard access, visible focus, labels, and mobile layouts?
- Are P1 actions gated rather than presented as live before their backend is ready?
