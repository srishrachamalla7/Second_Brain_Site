01 / The idea

Stop checking. Start knowing.

Your systems keep working when you're away from your laptop. PingLoom is meant to bring the important moments to you.

FOR DEVELOPERS

“Did the job finish?”

A long render or data job completes. Your server sends an event and you get a phone alert.

FOR AGENT BUILDERS

“Does it need me?”

An AI agent gets stuck or needs approval. It sends a structured event with a link to review.

FOR SMALL TEAMS

“Has anyone seen this?”

An operational issue appears in the shared inbox. One person acknowledges it so everyone knows who responded.

Think of it as a front desk for your software: events arrive, go to the right people, and stay in a searchable history.

Why someone would pay

Sending a basic push message is already possible with services like Firebase. The value here is the setup, routing, inbox, team visibility, retries and history wrapped into one usable product.

A focused first release

The scope is developer and operational alerts. Marketing campaigns, SMS, WhatsApp, email campaigns and an emergency on-call service are outside the initial plan.

01. Your system sends

One authenticated request to PingLoom's notification API.

02. PingLoom records

The event and a durable job are saved together.

03. A worker routes

It finds subscribed people and their active devices.

04. Firebase accepts

FCM takes the push request for Android.

05. You open & act

The app fetches details; you read or acknowledge.

Three different things: “Accepted” means saved by PingLoom. “Provider accepted” means Firebase accepted the push request. “Seen” means a user read it. Provider acceptance cannot prove that the phone displayed it; permissions and device conditions can delay or suppress alerts.

What would first-time setup look like?

Sign up and verify email → create a workspace and first project → install Android and sign in → allow notifications → register the device → create a server API key → send a test event. The target is a first real notification in under five minutes; this is a goal to validate.

03 / Product scope

One product now.
A platform later.

Product A / current build scope

Use the PingLoom app.

Developers send events; users receive them inside our shared Android app.

  • Android: sign in, register device, receive alerts, browse inbox, read and acknowledge.
  • Web dashboard: set up projects, create keys, send tests, inspect events and usage.
  • Backend: validate, store, route, retry and track events securely.
Product B / future, separate approval

Put it in your own app.

Other developers could later use PingLoom's infrastructure inside their own branded Android applications.

  • Embedded SDK: a reusable library for other apps.
  • The customer's Firebase project and end-user devices.
  • Separate recipient model and device-based metering.
  • Only after at least two SDK design-partner requests and separate approval.

04 / Under the hood

The important part:
don't lose the event.

The backend must save an event before saying it accepted it. A temporary worker or queue outage should leave recoverable work, rather than an event that disappears.

Your server or agentSends an event using a project API key.
→
FastAPI + PostgreSQLChecks access and saves event + outbox job in one transaction.
→
Worker → FCM → AndroidRoutes to devices, retries failures and records provider status.
Redis speeds dispatch.PostgreSQL remains the durable record. Redis loss must not erase accepted events.
The dashboard manages it.Next.js / TypeScript connects to the same API for setup, keys, event history and status.

Privacy by design

Push messages carry minimal information. The authenticated Android app fetches the full event. Teams must never see each other's projects, devices or event data.

Two kinds of credentials

People use user sessions. Servers use scoped API keys, shown once and stored as hashes. A server key must never be placed in Android or browser code.

What happens if the same event is sent twice?

An idempotency key identifies the request within a project for 24 hours. The same key and payload return the original event. Reusing the key with different data returns a conflict. Worker retries also must avoid duplicate delivery records and usage charges.

What happens when sending fails?

Workers claim jobs with expiring leases and retry temporary errors with increasing delays and a maximum attempt count. Permanently invalid device tokens are disabled. Exhausted jobs enter a failed/dead-letter state for inspection. A restarted worker can recover unfinished work.

Which technologies are planned?

Android: Kotlin, Jetpack Compose and Material 3. Web: Next.js and TypeScript. API: Python, FastAPI and Pydantic. Storage: PostgreSQL with Alembic migrations. Dispatch: Redis-backed workers, with arq or an equivalent and a PostgreSQL outbox. Push: FCM HTTP v1. Local services run in an isolated Docker Compose project.

What we'd measure

A median first alert under five minutes, activation of invited pilots, weekly usage, visible provider results, and tested tenant isolation. Healthy staging worker processing targets p95 under ten seconds; this is not a phone-display guarantee.

How paid rollout starts

Manual pilot invoices can come first. Public paid launch needs verified billing, receipts, cancellation, refunds and tax treatment. Android purchase prompts need policy review before implementation.

07 / Open questions & next steps

The plan is written.
These choices still matter.

Who are the first pilot users?

Find at least three teams with repeated alert needs and ask what they'd pay to solve them.

What is the final name & domain?

PingLoom is a working name. Brand, trademark, domain and store availability need verification before release.

Which production services?

Choose email and billing providers; configure Firebase credentials, mobile publishing and a support address.

What are the privacy commitments?

Set terms, privacy notice, data retention, account export/deletion and backup deletion policy.

How will we prove reliability?

Run real-device push checks, restart/retry tests, cross-workspace access tests and staged load checks.

Where will it run?

Use isolated infrastructure with a rollback plan. Existing production services require operator approval before changes.

The immediate engineering step

Build M0, then connect the first complete flow.

Start with a runnable local foundation. Progress through accounts → event ingestion → Android push → a usable dashboard. Validate the product with pilot teams while that foundation takes shape.

08 / Keep these words handy

The jargon, translated.

API
A defined way for one piece of software to ask another to do something. Here, your server asks PingLoom to record a notification.
FCM
Firebase Cloud Messaging, Google's push service used to reach Android devices.
Outbox
A database list of work still to be sent. It keeps accepted events recoverable if dispatch stops temporarily.
Worker
A background process that picks up stored work, finds recipients and calls the push provider.
Tenant isolation
Keeping each workspace's information and permissions separate from every other workspace.
Idempotency
Making a retry safe: sending the same identified request again doesn't create another event.
Acknowledgement
A shared record that someone responded to an alert. It is separate from each person's read/unread state.
MVP / P0 / P1 / P2
MVP is the first useful release. P0 is essential, P1 follows in paid beta, and P2 is later platform work.
