Distributor profit check

Bi2Bi · checked 20 Nov 2026 against the code (backend 3a67436) and read-only queries on the live database. Nothing was changed.

In short
  1. The profit screen has a real bug. One sugar bag shows ₹2,698 of fake profit.
  2. The cause is wrong prices saved on old Admin → distributor orders (11 lines, Aug–Oct). The method of picking the latest purchase is not the main problem.
  3. FIFO would still read those same wrong prices. FIFO alone does not fix this.
  4. The app does not show 40–50% profit today. North Zone shows 2.77% this month.
  5. Smaller fix: if a saved price looks too low, use the catalogue price. Also lock the cost on each sale.

1. How the profit screen works today

The distributor app's Profit screen calls the backend. The backend does three steps:

Take every consumer order delivered in the period
→
For each item, find the cost: the price on this distributor's latest delivered purchase from Admin for that exact pack
→
Profit = sales (without GST) − cost

If no purchase is found, it uses the catalogue distributor price. The code is in bi2bi-backend/app/distributor/analytics_helpers.py: build_profit_margin() calls last_purchase_costs().

6. What about batches?

The FIFO proposal also raises a fair point: the same product can be bought at different prices at different times. Today the distributor side has no batches. Each pack is one stock number in distributor_inventories (for example "20 bags"), and every unit gets the last price paid as its cost.

How big is this problem?

ProblemHow wrong profit getsHow common (North Zone)
No batches (old vs new price)A little Only as much as the price changed, e.g. ₹150 on a bagOnly 7 of ~490 packs were ever bought at more than one price
Wrong price saved on an Admin orderHugely e.g. ₹2,698 fake profit on one bag11 order lines (Aug–Oct)

So batches are a real gap, but a small one today. The wrong saved prices are the big problem. FIFO batches would not fix those, because the batch would carry the same wrong price.

Admin already has batches

Admin's own stock already uses batches: the inventory_batches table keeps purchase_price and quantity_remaining per batch, and reserve_admin_stock() in app/utils/stock_manager.py uses the earliest-expiring batch first. Only the distributor side lacks this. If distributor batches are built, copy this existing pattern instead of making a new one.

Two ways to handle it

Simple

Average cost

Keep one average price per pack and update it on each purchase: (old qty × old avg + new qty × new price) ÷ total qty. One extra column on distributor_inventories. It is an accepted accounting method, and cancels and returns need no batch logic.

Exact, more work

FIFO batches

Each delivery is a batch with its own price, and the oldest is used first. Every sale, cancel, return, edit, manual adjustment and held-stock change must update batches. It also needs a backfill for current stock.

Suggested order: fix the wrong prices first, then lock the cost on each sale. If the client wants batch accuracy after that, start with average cost. Move to FIFO only if it is really needed.

7. Suggested fix

Step 1 · small

Ignore bad purchase prices

If the saved purchase price is far below the catalogue price (for example under half), use the catalogue price. A few lines in last_purchase_costs() plus a test. No database change.

Step 2 · small

Lock the cost on each sale

Add purchase_cost to order_items and fill it at delivery. One column, so it needs a prod migration with approval and a backup first.

Step 3 · check

Find where the bad prices came from

Check whether new Admin orders still get wrong prices. If they don't, it was a one-time data problem from Aug–Oct.

Later · big

FIFO, only if needed

Use it if the client needs exact batch-level profit. It is a larger project, and it still needs correct prices to start with.

SELECT o.order_number, p.name, v.name AS pack, oi.unit_price,
       COALESCE(v.distributor_price, p.distributor_price) AS catalogue
FROM order_items oi
JOIN orders o ON o.id = oi.order_id
JOIN products p ON p.id = oi.product_id
LEFT JOIN product_variants v ON v.id = oi.variant_id
WHERE o.order_type = 'distributor_to_admin' AND o.status = 'delivered'
  AND oi.unit_price > 0
  AND oi.unit_price < 0.5 * COALESCE(v.distributor_price, p.distributor_price);

Why FIFO gives the same wrong answer here

FIFO keeps each delivery from Admin as a batch with its own cost. When a consumer buys, the oldest batch is used first. For the sugar bag, the only batch is the 9 Sep delivery, and its saved cost is ₹151.43. FIFO would use ₹151.43, the same as today's code. FIFO helps when correct prices change over time. It cannot fix a price that was saved wrong.
