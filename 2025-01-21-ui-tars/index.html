UI-TARS — Beginner Guide to Native GUI Agents

Original paper: UI-TARS: Pioneering Automated GUI Interaction with Native Agents Paper version covered here: v1, submitted 2025-01-21. Official code: bytedance/UI-TARS

This note is written for someone who can code but is new to GUI agents, multimodal models, and this research area. The goal is not to memorize the paper. The goal is to understand the machine well enough that you could build a smaller version.

0. Read this first

The one-minute explanation

A GUI agent is an AI that can use a computer the way a person does:

  • look at the screen,
  • decide what to do,
  • click or type,
  • look at the new screen,
  • decide again,
  • continue until the task is finished.

Older systems often glued together many separate pieces: one model understood the screen, another found buttons, some scripts decided what action to execute, and extra code stored memory or enforced workflows.

UI-TARS is trying to make the model itself become the agent. It takes the task instruction, a screenshot, and recent interaction history, and predicts a thought + action. The action can be something like Click(x, y), Type(text), Scroll(...), or a platform-specific action. The computer executes it, returns another screenshot, and the loop repeats.

The big idea is:

                TASK: "Book me a flight"
                         |
                         v
                 +----------------+
                 |    UI-TARS     |
                 | vision +       |
                 | reasoning +    |
                 | action          |
                 +-------+--------+
                         |
                  thought + action
                         |
             +-----------+-----------+
             |                       |
        Click(x,y)              Type(text)
             |                       |
             +-----------+-----------+
                         v
                    COMPUTER
                         |
                         v
                  NEW SCREENSHOT
                         |
                         +-------> UI-TARS again

The paper argues that getting this to work well requires solving four difficult things together:

  1. Perception — understand a crowded GUI screenshot.
  2. Action + grounding — know exactly what action to take and exactly where.
  3. Reasoning — think through multi-step tasks instead of reacting to one screen at a time.
  4. Learning from experience — collect failures and good trajectories, then train the model again.

The paper's main contribution is therefore less like “here is one clever neural-network layer” and more like “here is a full training recipe for turning a vision-language model into a native computer-use agent.” citeturn416863view0

1. The problem

First: what is a GUI agent?

Imagine you tell a human:

“Open the browser, search for flights from Berlin to Hyderabad, choose the cheapest option, and save it.”

A human does not receive an API called search_flights().

They see pixels.

They read text.

They understand buttons.

They decide what to click.

They remember what they already did.

They correct themselves when something goes wrong.

A real GUI agent has to do all of that.

Why is this hard?

A screenshot can contain hundreds of visual elements: tiny icons, text fields, buttons, menus, sidebars, popups, tables, images, and unrelated clutter. The model has to understand both what things are and where they are. citeturn910420view1

Then there is the action problem.

Knowing “click the Submit button” is not enough. The model must produce a valid low-level command and a precise location such as a screen coordinate.

Then there is the planning problem.

A task may require 20 actions. The agent has to remember what happened earlier and keep the final goal in mind.

Then there is the data problem.

Text and image models have huge training corpora, but high-quality records of people actually completing multi-step GUI workflows are much rarer. The paper calls this a fundamental data bottleneck for native GUI agents. citeturn416863view0

What was wrong with earlier approaches?

The paper describes an evolution:

STAGE 1
Rule-based automation
       |
       | rigid rules
       v
STAGE 2
Modular agent framework
       |
       | several separate models + tools + prompts
       v
STAGE 3
Native agent model
       |
       | one model learns the complete interaction behavior
       v
STAGE 4 (future direction in the paper)
Active / lifelong agent
       |
       | keep learning from experience with less human effort

The paper's complaint about modular systems is not that they never work. They can work very well for narrow tasks. The problem is that they require lots of manual engineering and task-specific glue, and can become brittle when the environment changes. citeturn416863view0

2. Mental model

Think of UI-TARS as a person operating a computer

A useful mental model is to imagine four pieces inside one brain:

             +----------------------------------+
             |            UI-TARS               |
             |                                  |
Screen ----> |  EYES      = perception         |
             |                                  |
History ---> |  MEMORY    = recent interaction |
             |                                  |
Goal ------> |  BRAIN     = reasoning          |
             |                                  |
             |  HANDS     = actions             |
             +----------------+-----------------+
                              |
                              v
                           COMPUTER

This is still one model. “Eyes”, “brain”, and “hands” are just a useful way to understand what capabilities the training is trying to teach.

The important shift

Traditional automation thinks:

"I know the DOM / API / exact workflow, therefore I can automate it."

UI-TARS tries to think:

"I can see the interface, so I can learn how to operate it."

That is why the paper emphasizes screenshot-only input. The model is not supposed to depend on an accessibility tree, HTML structure, or special application API at inference time. citeturn416863view0

4. How it works, step by step

Step 1 — Give the model the goal

Example:

"Open the browser and search for the cheapest flight to Hyderabad."

The instruction stays part of the context as the agent operates.

Step 2 — Give it the current screen

The main observation is a screenshot.

Unlike systems that first convert a GUI into structured text, UI-TARS is designed to directly consume the visual interface. The paper argues that this avoids platform-specific dependence on underlying system structures. citeturn416863view0

Step 3 — Give it recent history

The model also sees previous observations and actions.

Conceptually:

Instruction
+
Screen 1 -> Thought 1 -> Action 1
Screen 2 -> Thought 2 -> Action 2
Screen 3 -> Thought 3 -> ?

Because context is limited, the paper says it keeps only the last N observations, while retaining the interaction history in short-term memory. In the experiments, N is set to 5, and the authors mention token-budget constraints such as a 32k sequence length. citeturn910420view1turn405008view3

Step 4 — Think before acting

UI-TARS adds an explicit “thought” before each action.

SEE
 ↓
THINK
 ↓
ACT
 ↓
SEE NEW SCREEN
 ↓
THINK
 ↓
ACT

The paper calls this System-2 reasoning: deliberate reasoning for difficult, multi-step decisions. citeturn910420view1

Step 5 — Produce a normalized action

The model does not output a vague sentence such as “click the red button”. It produces one of the standardized actions.

Examples from the paper:

Click(x, y)
Drag(x1, y1, x2, y2)
Scroll(x, y, direction)
Type(content)
Wait()
Finished()
CallUser()

There are also platform-specific actions such as desktop hotkeys and mobile back/home/enter operations. citeturn910420view2

Step 6 — Ground the action precisely

This is an extremely important part.

Suppose the instruction is:

Click the red "Submit" button in the top-right.

The model must turn that meaning into coordinates.

The paper constructs grounding data from screenshot metadata, including bounding boxes and text. It converts the bounding box into a representative point, then trains the model to predict normalized screen coordinates so the behavior is less dependent on a particular resolution. citeturn910420view2

Think:

1920 x 1080 screen

actual pixel:
(1632, 141)

              ↓

normalized coordinate representation

              ↓

model learns "where" the target is

Step 7 — Execute on the machine

The environment performs the action.

For example:

UI-TARS -> Click(0.85, 0.13)
                    |
                    v
              OS / browser
                    |
                    v
             new screenshot

The next screenshot becomes the next observation.

That creates the agent loop.

Step 8 — Repeat until Finished()

The agent continues until the task succeeds, fails, or requests user intervention.

This is why GUI agents are fundamentally sequential: one bad click can change the entire future state of the task.

5. The architecture

5.1 The model backbone

UI-TARS starts from Qwen2-VL and continually trains 2B, 7B, and 72B scale variants. The paper reports roughly 50B training tokens for the developed models. citeturn405008view3turn416863view0

The paper is therefore not inventing a brand-new transformer from scratch.

A useful picture is:

                Qwen2-VL
                   |
          +--------+--------+
          |                 |
      general VLM       GUI training
          |                 |
          +--------+--------+
                   |
                UI-TARS
                   |
        GUI perception + reasoning
        + grounding + actions

MY TAKE: This is an important lesson when reading modern ML papers. The research contribution can be the data + objectives + training loop + system design, not a completely new base architecture.

5.2 Perception training

The authors build a GUI screenshot dataset with metadata such as:

  • element type,
  • depth,
  • bounding box,
  • text content.

They train several kinds of GUI understanding tasks: element description, dense captioning, state-transition captioning, question answering, and Set-of-Mark prompting. citeturn416863view0turn910420view1

Think of these tasks as teaching the model different levels of “looking”.

"What is on this screen?"
        |
        v
"What is this specific button?"
        |
        v
"What changed between screen A and B?"
        |
        v
"Which element answers this question?"
        |
        v
"Where exactly should I click?"

This is much richer than simply collecting screenshots with a label like button.

5.3 Unified action space

Different platforms naturally have different operations.

Without standardization you might have:

Web:     browser.click(...)
Android: tap(...)
Windows: mouse.click(...)
Mac:     something else

UI-TARS maps semantically similar operations into a shared action vocabulary.

That lets the model learn one conceptual language:

Click
Type
Scroll
Drag
Wait
Finished
...

The paper combines its own annotated trajectories with several open-source datasets and standardizes them into this unified format. citeturn405008view1

5.4 Grounding data

Grounding means:

“I know which GUI element you mean. Now tell me exactly where it is.”

The paper creates training pairs like:

SCREENSHOT
+
"red Submit button in the top-right"
            |
            v
      normalized (x, y)

This is one of the reasons GUI agents need much more than generic image understanding. The model must connect language, visual appearance, and geometry. citeturn910420view2

5.5 System-2 reasoning

The authors crawl around 6 million GUI tutorials and use GUI traces with inserted reasoning patterns. They explicitly encourage patterns such as:

Task decomposition
Long-term consistency
Milestone recognition
Trial and error
Reflection

They then augment traces with thoughts so the model learns a bridge between seeing the screen and selecting the next action. citeturn416863view0turn910420view3

This is important because:

Screenshot -> Action

is often too shallow for a difficult task.

They want:

Screenshot
   |
   v
"What is my goal?"
   |
   v
"What has already happened?"
   |
   v
"What should happen next?"
   |
   v
Action

5.6 Thought bootstrapping

There is a subtle problem with adding reasoning after the fact.

Suppose you already know the correct action is:

Click Submit

and then ask a model to invent a thought explaining it.

The thought may sound reasonable even if it is not the reasoning that actually caused the choice.

The paper therefore samples multiple thought + action candidates from an early model and keeps a thought when its sampled action matches the correct action. This tries to make the thought causally connected to the action instead of being a post-hoc explanation. citeturn405008view2

That is a genuinely useful idea to remember when building reasoning datasets.

5.7 Learning from online experience

Now comes the clever part.

The authors do not want humans to manually record every possible workflow forever.

Instead:

Task instructions
       |
       v
   Current model
       |
       v
Hundreds of virtual PCs
       |
       v
Raw trajectories
       |
       +--> bad / noisy
       |
       v
Filtering
  1. rules
  2. VLM scoring
  3. human review
       |
       v
Good trajectories
       |
       v
Fine-tune model
       |
       v
Better model
       |
       +------> collect more trajectories

The paper says this loop is run over multiple rounds on hundreds of virtual PCs. citeturn910420view4

5.8 Reflection tuning

Failure is especially valuable.

Imagine:

Goal: bookmark a page

Model thinks:
"Click bookmark"

but accidentally clicks:
"Close tab"

A dumb training dataset might throw the whole trajectory away.

UI-TARS instead teaches recovery.

WRONG ACTION
    |
    v
Observe the consequences
    |
    v
Recognize the mistake
    |
    v
Think about recovery
    |
    v
Correct next action

The authors annotate both error correction and post-reflection examples. Corrected steps are used for SFT; the method also constructs preference pairs so the model can learn that a corrected action is better than the erroneous one. citeturn910420view5

5.9 Why DPO appears here

DPO means Direct Preference Optimization.

Forget the name for a moment.

You have:

Same situation
      |
      +---- WRONG action
      |
      +---- BETTER action

Instead of only teaching “here is the right answer”, you can teach:

BETTER > WRONG

That is what the DPO stage is being used for: the model gets a preference signal between corrected and erroneous behaviors. citeturn910420view5

Let's build the smallest possible UI-TARS-style task.

Goal

"Open settings and turn on Dark Mode."

Observation 1

The model sees a home screen.

It thinks:

MY EXPLANATION:
I need to find the settings control first.

Action:

Click(900, 80)

Observation 2

Settings opens.

Now the screen contains:

Display
Notifications
Sound
Privacy
...

The model thinks:

I am in Settings. Dark Mode is likely under Display.

Action:

Click(410, 210)

Observation 3

Display settings are open.

The model sees:

Theme
  Light
  Dark
  System

Thought:

Dark is directly available. Select it.

Action:

Click(520, 370)

Observation 4

The screen changes to a dark theme.

Thought:

This tiny example shows why the agent needs all four capabilities:

Perception  -> understand the menu
Grounding   -> find the exact item
Reasoning   -> know the next step
Memory      -> remember that Settings was already opened

8. What is actually new?

The paper is not claiming one magic invention

The contribution is a stack of mutually reinforcing ideas.

Better GUI perception
        +
Unified actions
        +
Better grounding
        +
Explicit reasoning
        +
Experience collection
        +
Reflection / correction
        +
DPO from mistakes
        |
        v
More capable native GUI agent

The four ideas the paper emphasizes most strongly are:

1. Enhanced GUI perception

Teach the model to understand crowded GUI screenshots using multiple specialized data tasks. citeturn416863view0

2. Unified action modeling

Use one normalized action vocabulary across web, desktop, and mobile settings. citeturn405008view1

3. System-2 reasoning

Insert deliberate reasoning between perception and action and train on several reasoning patterns. citeturn910420view3

4. Iterative learning from experience

Let the agent act in virtual environments, filter the resulting trajectories, train again, and use errors for reflection and preference optimization. citeturn910420view4turn910420view5

MY TAKE: The most interesting contribution is probably the closed loop rather than any individual dataset.

model
  -> acts
  -> fails / succeeds
  -> records experience
  -> filters experience
  -> trains on experience
  -> becomes better
  -> acts again

That is the part that points toward more autonomous agents.

9. Results and evidence

The authors evaluate the system across three broad dimensions:

PERCEPTION
    |
GROUNDING
    |
AGENT TASK EXECUTION

Perception

For VisualWebBench, UI-TARS-72B scores 82.8, compared with 78.5 for GPT-4o in the paper's comparison. citeturn405008view3

Grounding

The paper reports strong grounding results across mobile, desktop, and web settings, including 38.1 on ScreenSpot Pro. citeturn416863view0

ScreenSpot

On ScreenSpot, the paper reports strong results from UI-TARS-7B and UI-TARS-72B, with different strengths across the mobile, desktop, and web categories. The table is important because it shows that being good at one GUI modality does not automatically mean being equally good everywhere. citeturn405008view4

Online agent tasks

For OSWorld and AndroidWorld, the paper reports:

OSWorld
UI-TARS-72B-SFT      18.8  (15 steps)
UI-TARS-72B-DPO      22.7  (15 steps)
UI-TARS-72B-DPO      24.6  (50 steps)

AndroidWorld
UI-TARS-72B-SFT      46.6

The paper compares these with Claude Computer Use at 14.9 / 22.0 on the corresponding OSWorld step settings and GPT-4o at 34.5 on AndroidWorld. citeturn405008view5

What do those numbers actually mean?

A benchmark score is not “the model is 46.6% as smart as a human”.

It means roughly:

Under this benchmark's task definition and evaluation procedure, this system successfully completed that fraction/score of the tested tasks.

So the useful question is not simply “which number is largest?”

The useful questions are:

What tasks were tested?
What inputs were allowed?
How many steps were allowed?
Was tool access allowed?
Was the model screenshot-only?
Was there human intervention?

Those details determine how impressive a number really is.

One interesting result: DPO helps

On OSWorld, the paper reports:

72B SFT -> 18.8
72B DPO -> 22.7   (15 steps)

The authors explicitly use DPO for OSWorld because that benchmark benefits strongly from the iterative improvement stage. citeturn405008view3turn405008view5

That is practical evidence for the paper's argument that learning from wrong trajectories is valuable.

10. Limitations / gotchas

1. The data pipeline is enormous

The paper is not saying:

"Install Qwen2-VL and add a clever prompt."

The system depends on large-scale screenshot datasets, action traces, reasoning annotations, millions of tutorials, online environments, multiple filtering stages, and large-scale training. citeturn416863view0turn910420view4

That makes exact reproduction expensive.

2. Screenshot-only does not mean “no infrastructure”

The model input can be screenshot-based while the surrounding system still needs an environment that captures screenshots and executes actions.

So the real architecture is:

MODEL
 +
SCREEN CAPTURE
 +
ACTION EXECUTOR
 +
COMPUTER ENVIRONMENT

The paper's “native model” claim is mainly about the decision-making model, not about magically eliminating the operating system integration layer.

3. The action space is still predefined

The model has a vocabulary of actions such as Click, Type, Scroll, Drag, and platform-specific controls. citeturn910420view2

That is already general, but it is not the same as an unrestricted computer API.

4. Context length forces a memory trade-off

The paper limits the model to the recent observations in its context because full history can become too large. citeturn910420view1

So long tasks still raise the classic question:

"What should the agent remember?"

5. Self-generated data can amplify mistakes

Online bootstrapping is powerful because it creates data cheaply, but it also creates the possibility of producing lots of bad examples.

That is why the paper needs:

rules -> VLM scoring -> human review

The filtering step is not a minor detail. It is what protects the next training round from being polluted by the previous model's mistakes. citeturn910420view4

6. Benchmark wins are not the same as universal reliability

The paper reports strong results on a number of benchmarks, but benchmark success does not mean an agent will safely and reliably operate every arbitrary desktop application.

MY TAKE: For real deployments, the environment, permissions, failure recovery, task boundaries, and safety layer matter just as much as raw model capability.

7. This note covers the paper's 2025 v1, not the later model lineage

The official UI-TARS repository has since moved on to later releases, including UI-TARS-1.5 and UI-TARS-2. Those are important when implementing the modern system, but they are not silently substituted for claims made by this original paper. citeturn168472view0

11. Build-it-yourself

First: do NOT try to reproduce the entire paper

A beginner implementation should be much smaller.

Your goal is to learn the architecture first.

Version 0 — tiny screenshot agent

                 +------------------+
Instruction --->|                  |
Screenshot ---->|   Vision model   |----> action text
History ------->|                  |
                 +--------+---------+
                          |
                          v
                    Action parser
                          |
                          v
                    PyAutoGUI / OS
                          |
                          v
                     new screenshot
                          |
                          +----> repeat

Step 1 — capture the screen

Use Python to capture the current desktop screenshot.

Step 2 — send screenshot + instruction to a VLM

Start with an existing vision-language model instead of training one.

Conceptually:

response = model(
    image=screenshot,
    text=instruction + recent_history
)

Step 3 — force a tiny action vocabulary

Start with:

CLICK(x, y)
TYPE(text)
WAIT()
DONE()

Do not start with 20 action types.

Step 4 — parse the response

Convert:

CLICK(820, 410)

into an actual mouse click.

Step 5 — close the loop

while not done:
    screenshot = capture_screen()
    thought, action = model(screenshot, instruction, history)
    execute(action)
    history.append((screenshot, thought, action))

Step 6 — add grounding data

Create examples such as:

Image
+
"Click the blue login button"
+
(x, y)

Normalize the coordinates.

Step 7 — collect trajectories

Start recording:

instruction
screen
thought
action
new screen
thought
action
...

Step 8 — deliberately keep failures

Do not only save successful runs.

Create examples like:

Wrong action
   |
   v
What changed?
   |
   v
What should I have done?
   |
   v
Correct action

This gives you the basic idea behind reflection tuning.

Step 9 — preference data

Create:

same state
   |
   +---- bad action
   |
   +---- good action

Then train a preference objective.

Step 10 — only then worry about scale

Once the tiny system works, you can explore:

more screenshots
more actions
more platforms
more trajectories
better filtering
larger models
online bootstrapping

Practical reproduction path

WEEKEND 1
Screenshot -> VLM -> CLICK / TYPE

WEEKEND 2
Add history + multi-step loop

WEEKEND 3
Add coordinate grounding dataset

WEEKEND 4
Record successful + failed trajectories

NEXT
Add reflection + preference training

LATER
Run many environments and bootstrap data

MY TAKE: This is the most important thing to carry from the paper. You do not need a 72B model to learn the architecture. You can reproduce the shape of the system with a much smaller model and understand each piece one at a time.

Official implementation starting points

The authors' codebase includes deployment/inference guidance, action parsing, coordinate processing, and a path toward running UI-TARS on desktop environments. Their public repository also points to a desktop agent implementation and browser automation ecosystem. citeturn168472view0turn168472search1

For the original 2025 paper, the most relevant thing to inspect in code is not just “how to call the model”. Study:

1. action format
2. coordinate normalization
3. screenshot -> model input
4. model output -> executable action
5. history format
6. benchmark environment loop

Those six pieces are the skeleton of the agent.

12. What I would remember

If you forget almost everything in this note, remember this:

A GUI agent is a control loop

SEE -> THINK -> ACT -> SEE -> THINK -> ACT

UI-TARS combines four things

Perception
   +

   +

The hard part is teaching the model:
