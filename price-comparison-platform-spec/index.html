Price Comparison Platform: Complete Technical and Product Specification

Prepared for: Srish Date: 01 September 2026 Status: Working specification, v1

0. How to read this document

Everything marked VERIFIED was checked against live sources on 01 September 2026 and the source is named. Everything marked ASSUMPTION is my judgement and you should test it before spending money on it.

The single most important thing in this document is Section 2. Several of the APIs that a generic plan would tell you to use were shut down or locked in the first half of 2026. If you build against a stale plan you will lose months.

1. Product definition

1.1 What it is

A price intelligence platform with two distinct product surfaces sharing one backend:

Surface A: Price Tracking (the core) User submits a product URL or picks from a catalogue. System monitors that item's price on a schedule and alerts the user when it drops below a threshold. Revenue comes from affiliate commission on the alert click, which lands at peak purchase intent.

Surface B: Comparison Search (the growth layer) User searches for an item. System returns the same item across multiple retailers with total landed cost, and picks a winner. Built second, because it depends on a matching engine that Surface A does not need.

1.2 What it is not, at least not in v1

Flights, hotels and ride-hailing are explicitly out of v1 scope. Reasoning in Section 2.4. They are not a smaller version of the same problem, they are a different problem with different data contracts, and the current API access situation makes them worse, not better, than in previous years.

1.3 Core product principle

A wrong price is worse than no price. Every design decision below optimises for correctness over coverage. It is better to track 500 items perfectly than 5 million items badly. Users forgive missing data. They do not forgive being sent to a checkout page showing a different number from the one in the alert.

The access gate, and this is the hard part:

VERIFIED: Eligibility is now 10 qualifying sales in the trailing 30 days. It was 3 under PA-API, and 1 before that. The window is rolling, so eligibility flips off the moment you drop below the threshold and flips back on when you climb again. Amazon's error for this is AssociateNotEligible (403).

A qualifying sale requires the buyer to complete checkout, not just add to cart, and to not return the item within the return window. Amazon's standard attribution window is 24 hours.

Implication for you: You cannot start on the Amazon API. You have to launch, drive real affiliate sales through some other mechanism, and the API turns on afterwards. Plan for Amazon coverage in Phase 2, not Phase 1. Design the retailer adapter interface so Amazon can be plugged in later without touching anything else.

3. The scraping layer, done properly

3.1 What you are actually fighting

VERIFIED: Modern anti-bot systems operate in layers and you must pass all of them simultaneously. The major vendors are Cloudflare Bot Management, DataDome, Akamai, HUMAN Security (formerly PerimeterX) and Kasada.

Cloudflare's ML v9 bot model became the default across all zones in Q1 2026 and weights JA4 TLS fingerprints and HTTP/2 frame ordering more aggressively than v8 did. The practical consequence: a clean residential IP alone is no longer enough. If your proxy terminates and re-encrypts TLS at a generic gateway, the bot score still fails.

Detection layers, in order:

  1. IP reputation. Datacenter IP ranges from major clouds are on published lists and fail immediately.
  2. TLS fingerprint (JA3/JA4). Python requests produces an instantly recognisable hash. So does Node with Axios.
  3. HTTP/2 frame ordering. Header order and frame sequence differ between real browsers and libraries.
  4. JavaScript challenge. Requires actual JS execution.
  5. Behavioural. Mouse movement, timing, navigation paths, session consistency.

3.2 The stack that works

Tier 1, cheapest, use for everything that will accept it:

  • curl_cffi (Python). VERIFIED: impersonates the TLS fingerprint of real browsers at the handshake layer. Free library. This single change removes the most common instant-block trigger for Python scrapers.
  • Rotating residential proxies. Match User-Agent to the impersonated TLS fingerprint. Mismatch is itself a signal.

Tier 2, for JS-challenge sites:

  • Playwright or Nodriver or SeleniumBase UC with anti-automation signals stripped. Randomised viewport, random 2 to 5 second delays, natural navigation paths, resource loading like a real browser.
  • Slow (5 to 30 seconds per page) and expensive. Use only where Tier 1 fails.

Tier 3, managed unblockers, when your own stack loses:

  • Oxylabs Web Unblocker, Bright Data Scraping Browser, ScrapingBee, Scrapfly, Apify.
  • Higher per-request cost, near-zero maintenance.

3.4 The AI layer, used correctly

You asked why AI does not solve scraping. Precise answer:

AI fixes parsing. AI does not fix fetching. Bot detection happens at the network layer, before any HTML reaches you. If Cloudflare returns a 403 or a Turnstile challenge, your model has nothing to read. The LLM sits downstream of the wall.

Where AI genuinely earns its cost: selector repair, not extraction.

Running a model on every price check is financially ruinous at scale. Instead:

1. FETCH        cheap request via curl_cffi + proxy
2. EXTRACT      cached CSS/XPath selector for this domain
3. VALIDATE     - did we get a number?
                - is currency correct?
                - is it within 40% of last known price?
                - is it not a strikethrough MRP?
4. IF VALID     store, done. Cost: fraction of a paisa.
5. IF INVALID   call LLM once with the raw DOM
                → re-derive selector
                → CACHE new selector for this domain
                → retry extraction
                → alert engineer if second failure

Model as selector repair on failure, cached per domain. This is the difference between a few dollars a month and a few thousand.

The trap AI introduces: a model returns a confident, plausible, wrong number when a page shows MRP, discounted price, bank-offer price, exchange price and subscribe-and-save price simultaneously. Indian ecommerce pages are especially bad for this. Your validation layer must catch it. Never trust a single model read for a price you show a user.

4.2 Why this shape

The retailer adapter interface is the most important design decision in the project. Every retailer is a plugin implementing one interface. Adding Amazon later, when your affiliate sales unlock the Creators API, must be a new file and zero changes anywhere else.

class RetailerAdapter(Protocol):
    domain_patterns: list[str]
    requires_js: bool
    tier: int  # 1=curl_cffi, 2=playwright, 3=managed

    def canonicalize(self, url: str) -> str: ...
    def extract_product_id(self, url: str) -> str: ...
    async def fetch(self, url: str) -> RawPage: ...
    def extract(self, page: RawPage) -> PriceSnapshot: ...
    def affiliate_link(self, url: str, sub_id: str) -> str: ...

canonicalize() matters more than it looks. Indian retailers append tracking junk, session IDs and referral params to every URL. Two users tracking the same item must resolve to the same row, or you fetch the same page twice and pay twice.

Note on price_snapshots: this table becomes your single biggest asset and your single biggest cost. 100,000 listings checked 4 times daily is 400,000 rows per day, 146 million per year. TimescaleDB with compression handles this; plain Postgres will hurt. Set a compression policy on data older than 30 days and a retention policy at 2 to 3 years.

4.4 Scheduling: adaptive, not fixed

Do not check everything at the same interval. Compute per listing:

base_interval = 24h

multipliers:
  × 0.25  if any user has an active watch near current price
  × 0.5   if price changed in last 3 checks (volatile item)
  × 0.5   during a known sale window (Big Billion Days, GIF, festive)
  × 2.0   if price unchanged for 14+ consecutive checks
  × 4.0   if zero users watching (catalogue-only item)
  × 8.0   after 3 consecutive fetch failures (backoff)

clamp to [1h, 7d]

This is the difference between a bill that scales with users and one that scales with catalogue size. It is the core economic insight of the whole project.

7.3 Operational essentials

  • Backups. pg_dump nightly to Backblaze B2 or Hetzner Storage Box. Test a restore before launch, not after your first incident.
  • Proxy failover. Two providers configured. When provider A's block rate crosses a threshold, cut over automatically. Single-provider dependency will take you down.
  • Circuit breaker per retailer. If a retailer's failure rate crosses 30% in a 15-minute window, stop fetching it entirely and alert. Hammering a site that has started blocking you turns a temporary block into a permanent one.
  • Blue-green deploys. Two API containers behind Caddy, health-checked, swap on deploy. Your scrapers must not stop during a release.
  • Secrets. Docker secrets or SOPS. Never .env in the repository.

The proxy line dominates everything. Three levers on it, in order of impact:

At a 2% alert-click-to-purchase rate that means about 8,750 alert clicks, which at 3 alerts per active user per month means roughly 3,000 active users. That is your break-even. Write that number on a wall.

9. Legal and compliance

I am not a lawyer and this is not legal advice. Get an Indian tech lawyer to review before launch. Budget for it.

9.1 India, where you operate

VERIFIED: The position is genuinely unsettled and you should not let anyone tell you otherwise.

  • IT Act 2000, Section 43 penalises unauthorised access to computer systems and entitles affected parties to compensation. In response to parliamentary questions, the Indian government took the view that intermediaries scraping publicly available data may fall under Section 43.
  • Indian courts have not yet determined whether ToS restrictions or robots.txt are enforceable. This is genuinely open. The CJEU has held that entities may impose binding contractual limits on scraping, which is persuasive but not binding in India.
  • DPDP Act 2023 applies to personal data of identifiable individuals. Product prices are not personal data, so your core dataset is outside it. But the moment you store seller names that identify individuals, or user reviews, you are a data fiduciary. Penalties reach Rs 250 crore.
  • Copyright Act 1957 applies to reproduced content. Prices are facts and facts are not copyrightable. Product descriptions and images are a different matter.
  • Aggravating factor to avoid: rotating IPs specifically to defeat a block a site has already imposed is conduct a court can read as knowledge that permission was absent, which is exactly the element a Section 66 allegation needs. This is a meaningful distinction. Distributing load is ordinary practice. Circumventing a block you have already received is not.

9.2 Practical risk-reduction rules

  1. Never scrape behind a login. This is the brightest line in every jurisdiction.
  2. Never store product images or descriptions. Store the price, the URL, the title and your own reference to their image URL. Hotlink or don't show it.
  3. Respect robots.txt even though enforceability is unclear. It is cheap insurance and it is the first thing anyone's lawyer will ask about.
  4. Rate limit hard. Well under what would degrade their service. Document your rate limits so you can show them.
  5. Identify your bot in the User-Agent with a contact URL. Counter-intuitive, but a site that can reach you will usually email before they sue.
  6. Stop immediately on receiving any notice. Do not negotiate first. Comply, then talk.
  7. Prefer the affiliate relationship. Once you are a Cuelinks publisher sending real sales to a merchant, your relationship with them changes character entirely. This is the strongest legal position available to you and it is another argument for launching on affiliate deep links.
  8. Affiliate disclosure is mandatory. FTC-style disclosure requirements apply if you have any US traffic; Indian norms are converging. Put it above the fold, not in the footer.

9.3 The Amazon-specific trap

Read the Amazon Associates Operating Agreement properly. It has historically restricted displaying Amazon price data obtained by means other than their API, and it restricts how long you may cache prices. If you scrape Amazon prices while holding an Associates account, you risk your account, which is your entire monetisation. Decide deliberately: either scrape Amazon and forgo Associates, or use Associates and only show Amazon prices from the Creators API. Do not do both accidentally.

10. Phased roadmap

Phase 0: Feasibility spike (Week 1 to 2). No app, no UI.

This exists to kill the project cheaply if it deserves to be killed.

  • ☐ Pick 5 target retailers. Suggested: Amazon.in, Flipkart, Croma, Reliance Digital, Vijay Sales.
  • ☐ Write one Python script per retailer. curl_cffi, one residential proxy, extract price from 40 real product URLs each.
  • ☐ Measure and record: success rate, block rate, bytes per fetch, seconds per fetch, which tier each site needs.
  • ☐ Run it continuously for 7 days. Blocks often appear on day 3, not day 1.
  • ☐ Extrapolate the real proxy cost per 1,000 listings per day.

Kill criteria. Do not proceed if: fewer than 3 of 5 retailers sustain above 90% success over 7 days, OR extrapolated proxy cost exceeds $500/month at 10,000 listings.

Phase 1: Tracking MVP (Week 3 to 10)

  • ☐ Core API, Postgres + TimescaleDB, Redis, worker pool
  • ☐ Retailer adapters for whichever survived Phase 0
  • ☐ Selector cache with LLM repair fallback
  • ☐ Adaptive scheduler
  • ☐ Auth, watches, alerts
  • ☐ Push via FCM, email via Resend
  • ☐ Mobile app: Home, Add Item, share-sheet intake, Item Detail, Settings
  • ☐ Cuelinks integration for affiliate deep links
  • ☐ Admin dashboard: adapter health, cost per listing
  • ☐ Deliberately excluded from Phase 1: cross-retailer matching, comparison search, web frontend beyond a landing page

Success criteria: 500 active users, 5,000 tracked listings, above 95% price accuracy sampled manually against live pages, first affiliate rupee received.

Phase 2: Comparison and scale (Month 4 to 7)

  • ☐ Product matching engine: GTIN/EAN where present, then brand + model normalisation, then embedding similarity on titles, with a human review queue for low-confidence matches
  • ☐ product_groups populated, comparison search live
  • ☐ Full Next.js web app with SEO-focused /p/ and /price-history/ pages
  • ☐ Apply for Amazon Creators API once 10 sales/30 days is sustained
  • ☐ Retailer count to 15 to 20
  • ☐ Multi-currency

Note on matching: this is the hardest engineering problem in the project and it is why it is in Phase 2. Indian retailers rarely publish GTINs. Titles vary wildly ("Samsung Galaxy S24 5G (Onyx Black, 256 GB)" vs "SAMSUNG Galaxy S24 5G 256GB Onyx Black"). Budget 6 weeks for this alone and expect a permanent human review queue.

Phase 3: Expansion (Month 8+)

  • ☐ Additional countries, starting with UAE or Singapore where Indian retailers already ship
  • ☐ EV charging module if it still looks interesting
  • ☐ Browser extension for desktop price comparison at checkout
  • ☐ Public API as a B2B product, which is where the real margin might be

11. The five things most likely to kill this

Ranked by probability, with the mitigation for each.

  1. Proxy cost outruns affiliate revenue. Most likely failure mode by a wide margin. Mitigation: Phase 0 measures this before you build. Adaptive scheduling and asset blocking are your levers. Break-even is roughly 3,000 active users; if user growth is slower than catalogue growth you are losing money on every listing.
  1. A major retailer blocks you permanently. Mitigation: circuit breakers, identified bot with contact details, and an affiliate relationship that gives them a commercial reason to tolerate you. Never more than 40% of your value concentrated in one retailer.
  1. Product matching never gets good enough. Mitigation: Phase 1 does not need it at all. If matching turns out to be intractable, you still have a working tracking product. This is why the phasing is ordered the way it is.
  1. Amazon Associates account terminated. Mitigation: the deliberate decision in Section 9.3. Do not scrape Amazon and hold an Associates account simultaneously without understanding the agreement.
  1. Nobody wants it. Mitigation: the share-sheet flow and the alert loop are your retention mechanics. If Week 4 retention after Phase 1 launch is below 20%, the problem is demand, not engineering, and no amount of additional retailers fixes it.

12. What to verify before writing any code

Things I could not confirm and you should, because they change the plan:

  1. Does Cuelinks expose a programmatic deep-link API to publishers? If it is dashboard and plugin only, you need to negotiate API access or find a network that has one. This is the highest-priority unknown in the entire document.
  2. Current Cuelinks commission rates for your target categories, and whether platform-type publishers are accepted at all.
  3. Amazon Creators API rate limits and TPS, which are not consistently documented publicly.
  4. Open Charge Map's CC BY-SA 3.0 share-alike scope, if you use it commercially. Share-alike could contaminate a proprietary dataset.
  5. Whether Cloudflare's Web Bot Auth opens a legitimate path for identified price-comparison agents. This launched May 2026 and is early, but if it matures it changes Section 3 substantially in your favour.

13. One-paragraph summary

Build a price tracking product, not a price comparison product, and build it for Indian ecommerce only. Tracking works because the user hands you the URL, which eliminates the matching problem entirely, and because cost then scales with demand rather than catalogue size. Run it on curl_cffi plus residential proxies with an LLM used only for selector repair on failure, self-hosted on Docker on a Hetzner box. Monetise through Cuelinks from day one because Amazon's API now requires 10 sales in a rolling 30-day window and Flipkart's direct program is closed. Skip travel entirely, because Amadeus Self-Service shut down on 17 July 2026, Kiwi closed to new developers, and session-based fares do not fit a URL-tracking architecture anyway. Spend two weeks on the Phase 0 spike before writing a line of product code, and kill the project without regret if the proxy economics do not clear.

Every VERIFIED item above was checked on 01 September 2026. API access terms in this space change frequently and several changed materially in the first half of 2026 alone. Re-verify anything in Section 2 before you build against it.
